## 问题与改动

用户最终确认默认1×正常，2×条纹一直保持，回1×恢复。自建命令模型配合真实加密控制器的640×48测试中，原速新2×帧8428字读回错误，App写像素/地址正确；物理WRITE期间出现高阻DQ。仅测试台降速后错误消失。这是集中写入压力的仿真证据，尚不能宣称已确定板上全部根因。

正式设计只修改 `src/user_source/hdl_source/team/bmp_center_zoom_2x.v`：新增默认开启的 `PACE_ZOOM_OUTPUT=1`；每接受一个2×像素后插入一拍间隔，在100MHz源时钟下最高每秒接受5000万像素。1×旁路继续使用原节奏。间隔仅在握手完成后设置，下游阻塞时有效像素保持，RGB/行末/帧末元数据继续由原缩放核心对齐。帧开始及复位清除间隔状态。

未更换缩放核心、FIFO、SDRAM控制器、PLL、时钟约束、顶层、音频或波形。该措施降低写FIFO输入密度，不把控制器busy当逐字ready，也不是控制器最大安全吞吐的通用保证；其他频率、图像格式与更快源流需要重新验证。原输入不可暂停，若后续写端持续堵塞，原overflow保护仍应阻止坏帧提交。

## 复现与验证入口

从例程根使用ModelSim：

```tcl
do run_board_zoom_tests.do
do run_board_zoom_control_tests.do
do run_board_zoom_fifo_tests.do
set diag_height 480
set forced_refresh 0
set output_div 1
set pace_zoom 1
do run_zoom_real_sdram.do
```

`output_div=1`表示测试台不做额外降速，修复来自实际设计RTL。`pace_zoom=0`仅用于在同一测试台关闭设计中的节奏控制、复现原速故障。

控制回归的合成SD桩补上集成版SPI参数，并将测试轮播间隔设为1s以保留原测试时长；正式控制器的3s参数未修改。该测试加载的是635888d集成控制器，BMP/SD/内存完成仍为合成源，不是全链路。

真实存储测试使用真实加密控制器和自建引脚命令模型，buffer1为整机307200；通过真实写链先写旧1×图，再并发读旧图/写新图，最后读回新1×及新2×图。像素源和视频节奏合成，读新图前等待100拍隔离排空；没有实际SD卡、HDMI、自动帧提交或官方器件时序模型。测试、模型与do脚本不加入TD设计源。

本次结果（2026-10-10）：

- 三组既有缩放、集成控制、FIFO回归均PASS；完整640×480真实控制器/自建命令模型测试中，新1×和新2×各307200字读回全部正确，旧图并发读取错误0、显示空读0、物理DQ高阻采样0。日志 `zoom_pacing_full_validation_20261010.log`，进程退出0。
- 同一测试台640×48仅关闭PACE_ZOOM_OUTPUT：1×正确，2×重新出现8428字错误，首错8960，并采到高阻DQ。日志 `zoom_pacing_disabled_control_20261010.log`，预期失败退出1，作为故障对照。
